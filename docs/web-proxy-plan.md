# Telegram Desktop WEB proxy: доработанный дизайн клиента

Серверная половина описана в `../tproxy-server/PLAN.md`. Формат её мультиплексирующих кадров и контракт `MessageChannel` являются авторитетными. Этот документ фиксирует рассмотренный дизайн Telegram Desktop и реализацию, которая теперь присутствует в этом дереве. Процедура выполнения, зависящая от сервера, намеренно вынесена отдельно в `docs/web-proxy-test-plan.md`.

## 1. Область и инвариант

WEB — это MTProxy, чьим основным транспортом является один скрытый нативный WebView, общий для всего процесса:

```text
Потоки сессий MTProto
  -> TcpConnection (существующая обфускация MTProxy и AES-CTR)
  -> WebProxySocket (один логический поток)
  -> WebProxy::Transport уровня процесса (один рабочий поток)
  -> один скрытый платформенный WebView
  -> внедрённый мост TelegramWebProxy с точным origin
  -> https://relay.example/[base-path/]?bridge=<derived-capability>#android=<nonce>
  -> HTTPS-транспорт
  -> хостинговый релей
  -> штатный MTProxy
  -> Telegram
```

Центральный инвариант: Telegram Desktop не открывает ни одного внешнего MTProto-сокета, пока активен WEB. Внешнее HTTPS-соединение устанавливает веб-движок скрытого WebView. Хостинговый релей видит только байты, уже преобразованные существующим уровнем протокола MTProxy; секрет MTProxy никогда не помещается в HTML или JavaScript.

Предыдущий путь через локальную страницу/системный браузер остаётся запасным. Telegram предлагает его только после того, как скрытый WebView недоступен или пропустил десятисекундный дедлайн запуска либо проверки работоспособности. Он никогда не открывает браузер автоматически.

## 2. Проектные решения

Первоначальный черновик оставлял несколько архитектурных вопросов открытыми. Теперь они зафиксированы:

1. На процесс приходится один транспорт и один скрытый WebView, а не по одному на аккаунт. Выбор прокси уже является процесс-глобальным, поэтому все аккаунты, использующие выбранный WEB-прокси, разделяют один мультиплексированный транспорт.
2. Транспорт владеет выделенным `QThread`. `QTcpServer`, принятые запасные сокеты, кадрирование WebSocket, состояние мультиплексирования и очереди живут там. Нативный WebView остаётся в потоке приложения и обменивается с рабочим потоком ограниченными сообщениями.
3. `WebProxySocket` и транспорт компилируются в основную цель `Telegram`. `connection_tcp.cpp` — единственное место фабрики, сохраняющее полный `ProxyData`, — уже в этой цели. Обратная зависимость от `td_mtproto` не вводится.
4. Сериализованное поле `host` хранит только каноническое строчное ASCII/IDNA A-label-имя хоста. Схема, порт, путь, query, фрагмент, user info, IP-адреса (включая сокращения WHATWG «заканчивается на число», такие как `127.1` или `0x7f.1`) и односегментные имена отклоняются. `port` фиксирован как `443`; `password` хранит секрет MTProxy; `user` хранит необязательный slug базового пути (§3.1). Операторам следует публиковать имена хостов WEB в форме ACE (`xn--…`): ввод ACE проходит без изменений на всех платформах, тогда как введённый вручную Unicode-хост отображается той версией Qt, с которой собран билд (IDNA2003/nameprep в сборках Qt 5.15 для Windows, UTS #46 nontransitional в Qt 6), поэтому хосты с deviation-символами (`ß`, `ς`, ZWJ, ZWNJ) или символами новее Unicode 3.2 могут нормализоваться в разные строки — а значит, в разные capability — на разных платформах.
5. WEB-записи вводятся вручную или импортируются из ссылок `tg://webproxy` / `https://t.me/webproxy` (см. §11); формы `tg://proxy?…` нет.
6. Неактивные WEB-записи не проверяются и удаляются из порядка кандидатов ротации прокси в v1. Проверка потребовала бы активации транспорта WebView и не должна создавать фоновые транспорты для каждого сохранённого прокси.
7. Родитель loopback — это один inline HTML-ответ без зависимостей. qrc-ресурс не добавляет ценности для такой маленькой страницы и создал бы ещё одну зависимость от генерируемых ресурсов.
8. Пока аутентифицированный loopback WebSocket явно открытой запасной страницы открыт, локальный родитель поддерживает пустой `RTCDataChannel` между двумя `RTCPeerConnection` на одной странице. Это best-effort защита от фонового жизненного цикла Chrome: она не использует медиа, STUN, TURN или удалённую сигнализацию, и неудача её установления никогда не валит транспорт.

## 3. Модель данных и персистентность

`MTP::ProxyData::Type::Web` добавляется в enum и сериализуется как код типа `4`. Существующий пятиполевой blob прокси остаётся неизменным:

```text
type | host | port | user | password
```

WEB отображает эти поля так:

| Поле | Значение для WEB |
|---|---|
| `host` | каноническое строчное ASCII/IDNA A-label-имя хоста |
| `port` | фиксированное значение `443` |
| `user` | пусто или канонический slug базового пути (§3.1) |
| `password` | существующий синтаксис секрета MTProxy |

Валидация требует непустого корректного DNS-имени хоста, канонического базового пути и поддерживаемого секрета MTProxy. Принимаются простые 16-байтовые секреты и секреты с `dd`-паддингом; секреты эмуляции TLS `ee` отклоняются, потому что штатный MTProxy ожидал бы внутреннюю запись эмуляции TLS, которую этот сырой релей намеренно не добавляет. Неизвестные будущие сериализованные коды типов десериализуются в `None`, а не в `Unexpected`, чтобы понижения версии пропускали неподдерживаемый прокси, а не падали.

### 3.1 Необязательный базовый путь

Адрес WEB-прокси — это имя хоста с необязательным базовым путём, `proxy.example.com` или `proxy.example.com/dobry-cola-super-app`, чтобы продакшн-origin мог продолжать обслуживать свой сайт и направлять в релей только этот префикс. Все эндпоинты WEB переезжают под префикс вместе; ничего не остаётся в корне:

```text
без базового пути:            базовый путь `dobry-cola-super-app`:
  GET  /?bridge=…               GET  /dobry-cola-super-app/?bridge=…
  POST /api/v1/session          POST /dobry-cola-super-app/api/v1/session
  POST /api/v1/up               POST /dobry-cola-super-app/api/v1/up
  POST /api/v1/down             POST /dobry-cola-super-app/api/v1/down
  GET  /api/v1/ws               GET  /dobry-cola-super-app/api/v1/ws
```

Адрес — это одно поле везде, где он вводится, отображается или передаётся: редактор, окно подтверждения, строка прокси и параметр `server` ссылки все несут `host` или `host/path`. Путь — это один или несколько разделённых `/` ASCII-сегментов, каждый соответствует `[A-Za-z0-9][A-Za-z0-9_-]*`, в сумме не более 128 символов, хранится без ведущего и замыкающего `/`. Экранирование `%xx`, Unicode и пустые сегменты отклоняются, а не исправляются, поэтому сериализованное значение и путь на проводе — одна и та же строка; `.` не входит в алфавит, поэтому точечные сегменты возникнуть не могут. Хост нечувствителен к регистру и хранится в нижнем регистре, а путь чувствителен к регистру и никогда не сворачивается, поэтому `Proxy.Example.COM/My-App` нормализуется в `proxy.example.com/My-App`, а вставленный префикс `https://` снимается при сохранении. Обслуживается только форма с замыкающим слэшем `/<slug>/`; клиент никогда не запрашивает `/<slug>`, и релей не обязан его перенаправлять, что добавило бы ещё одну наблюдаемую ветвь.

Slug — это пространство имён, а не учётные данные: он изолирует релей от остального сайта и держит обычные сканеры подальше от эндпоинтов транспорта, но bootstrap capability, сессионный bearer и секрет MTProxy остаются аутентификацией. Случайный slug повышает стоимость обнаружения развёртывания; он не заменяет ничего из перечисленного. Хранение его в иначе неиспользуемом поле `user` сохраняет сериализованный blob прокси неизменным и заставляет клиент без этой функции сообщать о записи как о невалидной, вместо того чтобы молча подключаться к корню хоста.

WEB ведёт себя как MTProxy во всей существующей модели:

- `secretFromMtprotoPassword()` принимает WEB.
- Прокси приложения Qt — `NoProxy`; WEB не влияет на обновления и общий HTTP-трафик.
- Пользовательское DNS-разрешение DC/прокси отключено, потому что имя хоста релея разрешает движок WebView или явно выбранный запасной браузер.
- Звонки остаются неподдерживаемыми.
- TCP MTProto включён, а обычное HTTP-соединение MTProto отключено.
- Эндпоинты DC игнорируются; хостинговый релей выбирает свою фиксированную цель штатного MTProxy.
- `initConnection` сообщает имя хоста релея и порт 443 как метаданные прокси клиента.

## 4. `WebProxySocket`

`mtproto/details/mtproto_web_proxy_socket.*` реализует `AbstractSocket` как логический байтовый поток поверх общего транспорта.

При `connectToHost` он регистрирует новый 24-битный идентификатор потока. Аргументы адреса и порта намеренно игнорируются. Он испускает `connected` после того, как активный транспорт завершил рукопожатие релея `WELCOME` и транспорт отправил `OPEN` для этого потока.

Записи конкатенируют одноразовый префикс соединения MTProxy и тело перед постановкой кадра `DATA` в очередь. Входящий `DATA` буферизуется и предоставляется через частичные вызовы `read()`. Каждое успешное чтение пополняет ровно столько байт кредита приёма кадром `WINDOW`. Потеря транспорта испускает `disconnected`; нарушения протокола, переполнение очереди и явные сбои транспорта испускают `error`.

Существующий `TcpConnection` продолжает владеть всей работой протокола MTProxy. Для WEB он использует `secretFromMtprotoPassword()` и `Protocol::Create(secret)` точно так же, как для MTProxy, затем выбирает `WebProxySocket` в единственном месте вызова фабрики сокетов.

## 5. Процесс-глобальный транспорт и потоки

`mtproto/web_proxy/web_proxy_transport.*` предоставляет фасад жизненного цикла в главном потоке и держит всё состояние ввода-вывода в своём рабочем потоке.

Жизненный цикл главного потока:

- `Activate(proxy)` создаёт рабочий поток при первом использовании, синхронно устанавливает выбранный валидный прокси и создаёт один скрытый WebView, когда выбранный WEB-прокси меняется; слушатель fallback остаётся несвязанным.
- `OpenBrowser(proxy)` связывает loopback-слушатель при необходимости, выпускает свежую одноразовую capability и открывает новую вкладку по явному запросу пользователя после того, как fallback был предложен.
- `Deactivate()` закрывает потоки, принятых клиентов и слушатель, когда приложение переключается с WEB, и уничтожает скрытый WebView.
- `Shutdown()` выполняется после остановки аккаунтов MTP и присоединяет рабочий поток.

Кандидат WebView выполняет своё собственное рукопожатие `HELLO` / `WELCOME` до того, как рабочий поток его примет. Запуск, инициализация моста, подтверждение записи и работоспособность — каждое ограничено по времени. Проваленный кандидат уничтожается, и другой кандидат пробуется после экспоненциально растущей задержки (от 2 до 30 с); fallback предлагается только когда сбой терминален (см. §8). Если повторная попытка удаётся, пока подключён запасной браузер, логические потоки переподключаются через WebView, а запасной сокет закрывается; ни одна сессия релея не мигрирует между транспортами.

Взаимодействие потока сессии использует поставленные в очередь вызовы в рабочий поток. Каждый поток хранит свой контекст сокета, и доставка из рабочего потока в сокет ставится в очередь в поток, владеющий этим сокетом. Уничтожение `WebProxySocket` синхронно снимает регистрацию в рабочем потоке до того, как базовый деструктор QObject сможет инвалидировать контекст. Это создаёт строгую границу упорядочивания: уже отправленные уведомления остаются во владении Qt и удаляются вместе с QObject, тогда как рабочий поток не может инспектировать или отправлять через контекст после возврата снятия регистрации. Глобальный указатель транспорта атомарен и остаётся живым, пока все сессии MTP не будут уничтожены.

Основные переходы состояния, отображаемые в настройках:

```text
Idle
  -> Connecting
  -> Connected
  -> WaitingForBrowser  (WebView недоступен, нездоров или провалился)
  -> Connecting         (пользователь подтвердил браузерный fallback)
  -> Connected

WaitingForBrowser
  -> Connected          (повтор WebView через 30 секунд удался)
```

## 6. Общие кадры релея

Все целые числа — big-endian. Реализация повторяет раздел 7 серверного плана:

```text
type:u8 | stream_id:u24 | length:u32 | payload:length
```

Каждое сообщение транспорта должно содержать один или несколько полных кадров. Парсер принимает конкатенированные кадры и отклоняет пустое сообщение или завершающий частичный кадр. Полезная нагрузка ограничена 1 MiB. Известные типы:

| Значение | Имя | Поток | Поведение клиента |
|---:|---|---:|---|
| `0x01` | `OPEN` | >0 | отправляется один раз после `WELCOME` |
| `0x02` | `DATA` | >0 | непрозрачные байты MTProxy |
| `0x03` | `CLOSE` | >0 | пустая полезная нагрузка; закрывает один логический сокет |
| `0x04` | `WINDOW` | >0 | четырёхбайтовая дельта кредита |
| `0x05` | `PING` | 0 | keepalive от релея к клиенту; отвечается `PONG` |
| `0x06` | `PONG` | 0 | отправляется только как точный ответ на `PING` |
| `0x10` | `HELLO` | 0 | клиент отправляет полезную нагрузку `01` для протокола v1 |
| `0x11` | `WELCOME` | 0 | пустая полезная нагрузка; должен быть первым кадром релея |
| `0x12` | `AUTH_CHAL` | 0 | зарезервирован для relay-auth v2, отклоняется в v1 |
| `0x13` | `AUTH_RESP` | 0 | зарезервирован для relay-auth v2 |
| `0x1f` | `BYE` | 0 | проваливает текущие логические потоки и закрывает транспорт |

Входящий `OPEN`, кадр потока на нулевом потоке, кадр сессии на ненулевом потоке, некорректный `WINDOW`, данные сверх предоставленного кредита, неизвестный живой поток или неизвестный тип — это ошибка протокола для v1. Клиент хранит до 4096 недавно закрытых идентификаторов потоков. Корректные `DATA`, `WINDOW` и `CLOSE`, уже находящиеся в полёте для сохранённого идентификатора, отбрасываются; это предотвращает провал несвязанных мультиплексированных потоков из-за обычной гонки закрытия в разных направлениях.

## 7. Управление потоком и границы памяти

Оба направления начинают с неявного окна 4 MiB на поток.

Управление нисходящим потоком точное: `DATA` от релея расходует кредит приёма клиента, и Telegram Desktop возвращает его только когда `WebProxySocket::read()` сливает байты в движок MTProto. Это естественным образом ограничивает непрочитанные данные каждого сокета.

Восходящий поток имеет ограничение, которое пропустил первоначальный черновик: `AbstractSocket::write()` возвращает `void` и не предоставляет события writable/backpressure, поэтому он не может остановить вызывающего MTProto и возобновить позже. Поэтому клиент:

- расходует предоставленный релеем кредит отправки перед испусканием каждого кадра `DATA`;
- разбивает исходящие данные на кадры не более 64 KiB;
- ставит избыточные данные в очередь на поток;
- объединяет смежные записи до 64 KiB и избегает копирований при удалении из начала;
- проваливает поток, если его ожидающий восходящий поток превышает 8 MiB или 1024 элемента в очереди;
- ограничивает все поставленные в очередь межпоточные восходящие данные 64 MiB и 8192 элементами;
- приостанавливает сброс потоков, когда очередь записи процесс-глобального loopback-сокета достигает 4 MiB, и возобновляет по мере слива байтов;
- резервирует 64 KiB этого бюджета сокета для управляющего трафика и ограничивает отдельную управляющую очередь 64 KiB / 1024 кадрами;
- планирует готовые потоки round-robin, не более 256 кадров за один ход рабочего потока.

Если активный транспорт не продвигает запись 30 секунд, транспорт проваливается, и его заменяет обычная логика переподключения MTProto. Исчерпание бюджета потока или транспорта также проваливается сразу, не позволяя бесконечно копить поставленные в очередь события рабочего потока. Если измерения покажут, что устойчивые многомегабайтные загрузки могут исчерпать эти границы, будущее изменение должно добавить writable-backpressure в контракт `AbstractSocket`, а не молча растить память.

### 7.1 Производительный конверт и сравнение со встроенным HTTP

Хостинговый мост пакетирует до 2 MiB и ведёт восходящий и нисходящий потоки одновременно. Каждое направление в v1 секвенируется по схеме stop-and-wait, что даёт ограничение занятого направления только по RTT: 40, 20, 10 и 4 MiB/s при 50, 100, 200 и 500 мс RTT от веб-движка до релея соответственно. Фактические результаты включают время передачи, плечо релей–MTProxy и планирование веб-движка. Окно потока 4 MiB — это два пакета транспорта, чтобы возвращённый кредит не воспроизводил прежнее узкое место в 256 KiB.

Встроенный HTTP-транспорт MTProto тоже копирует тела запросов/ответов и использует HTTP wait request, но `QNetworkAccessManager` может держать несколько POST активными. Поэтому сегодня WEB более чувствителен к RTT. Эта сериализация, фиксированный размер пакета и большинство копирований буферов — это выбор реализации; ограниченный упорядоченный конвейер или совместимый потоковый транспорт может их сузить. Неотъемлемая стоимость WEB остаётся: один платформенный веб-движок, дополнительный путь релей/TLS, нативная граница JavaScript и head-of-line-подверженность общего транспорта. Явный браузерный fallback добавляет пересечения MessageChannel и loopback. При удачно размещённом релее обычные сообщения и умеренные медиа должны быть в том же практическом классе, что и встроенный HTTP-транспорт, тогда как прямой TCP/MTProxy остаётся эталоном по задержке и пиковой пропускной способности.

## 8. Граница скрытого WebView

`lib_webview` предоставляет `WindowMode::Hidden`, `HiddenSupported()` и `Window::valid()`. Скрытый режим создаёт платформенный веб-движок без окна Telegram и без встроенного Qt-виджета:

- macOS сохраняет нативный `WKWebView`, не оборачивая его в `QWindow` или виджет;
- Windows использует современный WebView2 с невидимым контроллером и без виджет-контейнера;
- все остальные платформы держат WebKitGTK в существующем вспомогательном процессе и прикрепляют его к немаппированному нативному GTK-toplevel, не создавая embed/compositor-виджет.

Скрытый режим не устанавливает обычный UI диалога WebView. Навигация в новое окно отклоняется. Транспорт разрешает только точную каноническую HTTPS-навигацию к мосту. Мост внедряется только в документ верхнего уровня, и нативные сообщения принимаются только из сконфигурированного HTTPS-origin (сравнение в форме ACE, поэтому IDN-хосты на TLD из белого списка Qt работают); сообщение без исходного URL отклоняется. Очищенный URL истории `https://host/` принимается для сообщений, но не как свежая навигация.

Транспорт открывает WebView с установленным `restrictedOrigin`, что переводит `lib_webview` в его ограниченный профиль: эфемерное хранилище на каждый транспорт; cookies никогда не принимаются; загрузки, новые окна, навигация подфреймов, запросы разрешений, диалоги аутентификации и запросы не-`https`/`wss` к любому другому хосту отклоняются; и lock-скрипт на старте документа, внедряемый в каждый фрейм (чтобы свежий `about:blank`-реалм не мог его обойти), который устанавливает `<meta>` CSP, разрешающую только inline-скрипт и соединения к точному origin, и определяет `undefined` поверх storage, workers, audio, speech, WebRTC (`RTCPeerConnection` и родственники), `WebTransport`, `WebAssembly`, notifications, payment, presentation, media capture, file pickers, `navigator.credentials/mediaDevices/getUserMedia/wakeLock/share/xr/getGamepads/storage/locks/sendBeacon/permissions` и подобного. Таким образом, страница оператора всегда получает только inline-скрипт плюс `fetch`/`WebSocket` к своему собственному origin.

Принуждение на уровне движка подкрепляет скрипт на каждой платформе:

- Windows (WebView2): ограниченный профиль владеет своей папкой пользовательских данных и своим процессом браузера; он работает с `--disable-features=msSmartScreenProtection` и `IsReputationCheckingRequired = FALSE` (чтобы URL capability никогда не сообщался в SmartScreen) и `--force-webrtc-ip-handling-policy=disable_non_proxied_udp` (без прямого UDP); запросы к другим origin получают 403 из `WebResourceRequested`; сообщения страницы не отражаются обратно, а запросы новых окон никогда не доходят до системного браузера.
- macOS (WKWebView): `peerConnectionEnabled` и `mediaDevicesEnabled` выключаются через тот же путь KVC, что используется для `developerExtrasEnabled`, а на macOS 13+ конфигурация включает Lockdown Mode (без JIT, WebAssembly или WebGL). Lock-скрипт — это `WKUserScript` с `forMainFrameOnly:NO`.
- все остальные платформы (WebKitGTK): `enable-webrtc` и `enable-media-stream` устанавливаются в false, если установленный WebKitGTK их предоставляет; путь API 4.0/4.1 включает песочницу веб-процесса (`webkit_web_context_set_sandbox_enabled`); движок уже работает в отдельном процессе `-webviewhelper`, а lock-скрипт внедряется с `WEBKIT_USER_CONTENT_INJECT_ALL_FRAMES`. Лимит script-message помощника — 2 MiB, достаточно для полного 1 MiB кадра релея в base64.

Debug-сборки выполняют пробу после первого сообщения моста и пишут строку в лог, если `RTCPeerConnection`, `WebTransport` или `WebAssembly` всё ещё достижимы в верхнем фрейме или в только что созданном `about:blank`-iframe.

Страница получает объект `TelegramWebProxy` с точным origin на старте документа. Он использует тот же развёрнутый контракт моста, что и Android: свежий 32-байтовый URL-safe nonce в `#android=`, версия 1 `tproxy-android-init` и сырые кадры релея. Поскольку общий API WebView для десктопа передаёт строки, бинарные кадры пересекают нативную границу как строгий base64 и подтверждаются монотонно возрастающей последовательностью записи. Нативная очередь ограничена 8 MiB / 1024 элементами.

Кандидат должен получить ровно один валидный `WELCOME`, и только после nonce'ного `tproxy-android-init`. Дедлайн рукопожатия — десять секунд, продлеваемый ещё на десять секунд каждый раз, когда мост сообщает `status: connecting|reconnecting` (собственный бюджет повторов моста ~23–28 с), до 45 секунд с начала навигации. После принятия главный поток опрашивает JavaScript каждые три секунды; десять секунд без валидного сообщения моста или десять секунд без подтверждения нативной записи проваливают транспорт.

Транспорт держит не более 512 кадров в полёте в сторону WebView (управляющие кадры могут использовать последние 64 из них) и объединяет `WINDOW`-гранты на поток, испуская их при накоплении 256 KiB или через 20 мс, так что жёсткий лимит транспорта в 1024 элемента недостижим в нормальной работе.

Когда транспорт отбрасывается после принятия, управляющий close оценивается в странице, и WebView держится живым ещё 200 мс, чтобы мост мог отправить свой `DELETE /api/v1/session`.

Сбои WebView повторяются с экспоненциальной задержкой от 2 до 30 секунд (сбрасывается при каждом успешном принятии). Строка всё это время показывает `connecting`; состояние `WaitingForBrowser` и окно подтверждения, предлагающее fallback через системный браузер, появляются только при терминальном сбое: скрытые WebView не поддерживаются на платформе (проверяется один раз за активацию; ничего не повторяется), создание WebView не удалось, или три последовательных сбоя без единого принятия. После этого повторы продолжаются в фоне с максимальным интервалом.

## 9. Граница явного fallback через системный браузер

Рабочий поток связывает `QHostAddress::LocalHost` на эфемерном порту только когда пользователь просит fallback (`Открыть браузер`), и объявляет числовой origin `http://127.0.0.1:<port>`. Слушатель снова закрывается после того, как вкладка браузера аутентифицировалась, когда выпущенная capability истекает неиспользованной, когда скрытый WebView берёт верх, и при деактивации, поэтому слушающего порта нет, если fallback не запрашивался. Перезагрузка страницы после этого требует свежего `Открыть браузер`.

`GET /` отдаёт inline-родителя с `no-store`, `nosniff`, `no-referrer` и свежим на каждый ответ nonce скрипта. Его строгая CSP разрешает только привязанный к nonce bootstrap, сконфигурированный HTTPS-origin iframe и его точный локальный эндпоинт WebSocket.

`GET /transport` переключается на RFC 6455 только когда выполняются все условия:

- адрес пира — loopback;
- метод/путь — ровно `GET /` или апгрейд `/transport`;
- `Host` — точный числовой loopback-хост и текущий порт;
- `Origin` — точный origin loopback-страницы;
- присутствуют `Upgrade`, `Connection`, версия 13 и валидный 16-байтовый ключ;
- дублирующиеся имена HTTP-заголовков отклоняются;
- тела запросов и transfer encoding отклоняются на локальной границе GET;
- блок HTTP-заголовков не более 16 KiB.

Клиентские кадры WebSocket должны быть маскированы. Парсер поддерживает 7/16/64-битные длины, text, binary, continuation, ping, pong и close с лимитом сообщения 2 MiB. Серверные кадры немаскированы, как требует RFC 6455.

Принятый локальный клиент должен завершить аутентификацию capability в течение десяти секунд. Это ограничивает молчащие HTTP-соединения и неаутентифицированные WebSocket, чтобы они не могли бесконечно держать все 32 слота локальных клиентов.

Первое полное сообщение WebSocket должно быть UTF-8 JSON:

```json
{"t":"auth","token":"<capability>","browser":"<user agent summary>"}
```

Capability — это 256 случайных бит, URL-safe base64, переносимые только во фрагменте URL браузера. Страница немедленно убирает её из видимого URL. Она одноразовая, истекает через пять минут и заменяется при открытии другой вкладки. Свежеаутентифицированная вкладка заменяет предыдущую аутентифицированную вкладку и заставляет потоки MTProto переподключаться, а не пытаться о неподдерживаемом возобновлении между вкладками.

После аутентификации:

- клиент сначала отправляет текстовое сообщение `{"t":"bridge","url":"https://<host>/?bridge=<capability>"}`; таким образом, производная capability передаётся только вкладке, доказавшей владение одноразовым токеном из фрагмента, и никогда не встраивается в неаутентифицированную страницу `GET /`;
- бинарные сообщения WebSocket несут один или несколько общих кадров релея;
- текстовые сообщения со страницы могут только сообщать состояние моста как `{"t":"status","state":"connecting|connected|reconnecting|failed"}`;
- pings от неаутентифицированных клиентов игнорируются.

Если аутентифицированный браузер не вернёт требуемый `WELCOME` в течение 30 секунд, клиент проваливает этот транспорт и закрывает свой локальный WebSocket. Это превращает неверную capability моста, сбой загрузки iframe или обычный публичный ответ в восстановимое состояние `unavailable`, а не оставляет строку настроек в состоянии connecting навсегда.

## 10. Контракт родительской страницы и хостингового iframe

Локальный родитель читает и очищает свою независимую одноразовую loopback-capability, подключает локальный WebSocket, ждёт текстового сообщения `bridge` и только затем создаёт iframe (с ограниченными флагами `sandbox` и `referrerPolicy`, установленным до `src`) для этого URL, который должен начинаться с `relayOrigin + base + '?bridge='`, и устанавливает `MessageChannel`.

Родитель также создаёт два `RTCPeerConnection` на одной странице с пустым списком ICE-серверов, обменивается их описаниями только в локальном JavaScript, переписывает обменянные host-кандидаты на `127.0.0.1` и сохраняет открытый, в остальном простаивающий `RTCDataChannel`. Это избегает зависимости поведения самоподключения от mDNS/интерфейсов и держит RTC-пакеты на loopback. Никакое RTC-состояние не раскрывается хостинговому iframe. Защита стартует вместе с аутентифицированным loopback WebSocket, закрывается с ним или на `pagehide` и пересоздаётся на `pageshow` или с ограниченной задержкой, если локальное RTC-соединение проваливается. Браузеры без работоспособного WebRTC продолжают с обычным транспортом. Защита снижает риск фонового замораживания Chrome, интенсивного троттлинга таймеров и обычного автоматического отбрасывания, но это не зависимость корректности: ручное закрытие вкладки, завершение браузера или ОС и срочное отбрасывание остаются обычной потерей транспорта.

Для канонического имени хоста `H`, канонического базового пути `P` (пусто в корне хоста) и декодированных байт секрета WEB `S`, включая ведущий байт `dd`, если он есть, вычисляется:

```text
base     = P is empty ? "/" : "/" + P + "/"
context  = P is empty
             ? UTF-8("tdesktop-web-proxy-bridge-v1\n" + H)
             : UTF-8("tdesktop-web-proxy-bridge-v2\n" + H + "\n" + P)
bridge   = base64url-no-padding(HMAC-SHA256(key=S, message=context))
bridgeUrl = "https://" + H + base + "?bridge=" + bridge
```

Корневая производная — это замороженный контекст v1, байт в байт. Базовый путь использует свой собственный контекст v2, поэтому capability, выпущенная для одного префикса, не аутентифицирует ничего ни на другом префиксе, ни в корне.

Нормативные векторы:

| Имя хоста | Базовый путь | Декодированный секрет (hex) | `bridge` |
|---|---|---|---|
| `proxy.example.com` | | `000102030405060708090a0b0c0d0e0f` | `MHLEY5PmW1GWqJkSrlmJpvJUiLhBH_QKy6yKg8a0JPk` |
| `proxy.example.com` | | `dd000102030405060708090a0b0c0d0e0f` | `IpJrt3e7sKtzPyoXy6w-Zj6GGEvsvclN66JzQEfPYLA` |
| `proxy.example.com` | `dobry-cola-super-app` | `000102030405060708090a0b0c0d0e0f` | `hHz99Xs93EN1j91G9gpNepXwGNNt5YdAFkEVk_LlqdQ` |
| `proxy.example.com` | `dobry-cola-super-app` | `dd000102030405060708090a0b0c0d0e0f` | `TGUkZaevsavLbHvlNWipnRoYxgzZ51ioWvbxgGT3wHo` |

Производная capability конструируется в памяти в tdesktop и нигде не сохраняется и не показывается в настройках прокси. При загрузке iframe родитель отправляет ровно:

```javascript
iframe.contentWindow.postMessage(
  { t: 'tproxy-init', v: 1 },
  relayOrigin,
  [channel.port2]);
```

Целевой origin точный и никогда не `*`. Бинарные сообщения передаются как `ArrayBuffer` в обоих направлениях. Кадры, полученные локально до инициализации iframe, кратко ставятся в очередь и передаются после инициализации. Родитель не разбирает общие кадры релея и никогда не получает секрет MTProxy. И очередь восходящего потока хостинга, и очередь локального WebSocket родителя ограничены 32 MiB; очередь хостинга также ограничивает сохранённые объекты буферов 16384. Превышение любой из границ закрывает транспорт, а не растит память браузера без предела.

Объекты статуса iframe обновляют видимую вкладку и пересылаются в tdesktop. Когда локальный WebSocket закрывается, родитель отправляет `{t:'close'}`, чтобы мост мог удалить свою сессию релея. Закрытие запасной вкладки сбрасывает локальный WebSocket и отключает его логические сокеты. Telegram Desktop не открывает вкладку автоматически. Он продолжает пробовать скрытый WebView с задержкой из §8. Перезагрузка не может переиспользовать очищенную одноразовую loopback-capability (и слушатель закрывается после аутентификации вкладки); после очередного сбоя окно подтверждения или меню строки может выпустить свежую capability и открыть новую вкладку.

## 11. Настройки и интеграция с приложением

Настройки прокси предоставляют четвёртую радиоопцию `WEB`. Редактор показывает:

- одно поле адреса прокси, содержащее `host` или `host/path`, которое также принимает вставленный префикс `https://` и снимает его при сохранении;
- одно поле секрета MTProxy;
- без пары host/port сокета и без полей имени пользователя/пароля.

Строки отображают только этот адрес. Неактивные строки WEB показывают `not tested`, не создавая чекер, WebView или вкладку браузера. Только точная активная строка WEB показывает живой жизненный цикл транспорта. `Открыть браузер` предлагается только после того, как встроенный транспорт провалился. WEB остаётся неподдерживаемым для звонков. Поскольку бэкенд по-прежнему MTProxy, WEB сохраняет существующее раскрытие спонсируемого прокси (в редакторе и в подтверждении ссылки) и поведение обновления промо. Как и MTProxy, имя хоста WEB — это то, что `initConnection` сообщает как адрес прокси; трафик QNetworkAccessManager вне MTProto не маршрутизируется через транспорт WEB.

Ссылки WEB используют `webproxy`, канонический адрес и секрет MTProxy. Порт 443 неявный и не принимается из ссылки и не отображается в её подтверждении:

```text
https://t.me/webproxy?server=<address>&secret=<secret>
tg://webproxy?server=<address>&secret=<secret>
```

`<address>` — это percent-encoded `host` или `host/path`, поэтому базовый путь путешествует в том же параметре, что и `proxy.example.com%2Fdobry-cola-super-app`. Отдельного параметра пути нет. Ссылка, несущая путь, также кодирует свой секрет как unpadded base64url от `0x70` плюс реальный секрет, чтобы клиент без поддержки пути сообщал о неподдерживаемом типе прокси и просил пользователя обновиться, вместо того чтобы нормализовать адрес в пустой хост и предлагать к нему подключиться. Корневая ссылка сохраняет простой секрет и всё ещё работает в таких клиентах. Переход по любой ссылке показывает адрес и секрет с одним действием подключения. Она не проверяет статус и не включает прокси до вызова этого действия. Сохранённые записи WEB можно делиться как публичной ссылкой или QR-ссылкой прямого скелета.

Изменения прокси приложения настраивают/деконфигурируют веб-транспорт до перезапуска сессий MTP. WEB следует пути MTProxy в `Session`, `SessionPrivate` и `TcpConnection`; глобальный прокси Qt остаётся для него отключённым. Ротация прокси и чекер доступности настроек намеренно пропускают неактивные записи WEB, вместо того чтобы открывать WebView или браузер.

## 12. Ограничения и границы

- Слушатель — только IPv4 loopback и валидирует пира, host и origin.
- Локальная аутентификация требует выпущенной fragment-capability.
- В локальном протоколе нет команды произвольного назначения. `OPEN` происходит только из tdesktop, и релей, как ожидается, набирает один сконфигурированный штатный MTProxy.
- Сконфигурированное значение — каноническое DNS-имя хоста плюс необязательный канонический базовый путь; HTTPS и порт 443 фиксированы.
- URL моста содержит только разделённую по домену производную capability, никогда не сырой секрет MTProxy.
- Границы кадра, WebSocket, HTTP-заголовков, числа локальных клиентов, окна приёма и ожидающего восходящего потока предотвращают неограниченную буферизацию.
- Родительский iframe использует только `sandbox="allow-scripts allow-same-origin"`.
- Полезные нагрузки и секреты никогда не логируются этим кодом клиента.
- Сбои сокета WEB не вызывают прямой HTTP-fallback синхронизации времени tdesktop.
- `CLOSE` — это аборт в обоих направлениях: недоставленные `DATA` на закрытом потоке отбрасываются, точно как в существующем TCP-пути tdesktop, который никогда не делает half-close.
- Модель доверия: оператор полу-доверенный. Его страница исполняет JavaScript внутри ограниченного профиля (§8) и никогда не видит секрет MTProxy; производная capability — это стабильный bearer для (host, secret). Локальный процесс не может получить capability из loopback-слушателя (§9); ему нужен `tdata`.
- Аутентификация релея (`AUTH_CHAL` / `AUTH_RESP`) не реализована в v1. Её добавление требует полностью специфицированного контекста challenge и серверных тестовых векторов; она должна вычисляться в tdesktop без передачи секрета в JavaScript.

## 13. Требования к хостинговому серверу перед тестированием выполнения

Сервер должен предоставить всё это до того, как отдельный план тестирования сможет пройти:

1. `https://<hostname>/[<base-path>/]?bridge=<derived-capability>` реализует точную производную, fallback обычного сайта, `MessageChannel`, контракты close и status выше, причём каждый эндпоинт транспорта находится под тем же префиксом.
2. Его CSP разрешает фрейминг со случайных числовых loopback-origin. Подходящий источник — `http://127.0.0.1:*`; `X-Frame-Options` не должен блокировать встраивание.
3. Мост принимает кадр `HELLO` v1, устанавливает надёжный упорядоченный транспорт и возвращает `WELCOME` до трафика потоков.
4. Релей реализует все кадры потоков v1, неявные окна 4 MiB и дедуплицированную/курсорную надёжность для поллинг-транспортов.
5. Каждый `OPEN` набирает только сконфигурированный эндпоинт штатного MTProxy.
6. Хостинговый код никогда не логирует полезные нагрузки кадров.
7. HTTPS long-poll транспорт v1 работает; развёрнутый мост не требует публичного WebSocket или другого транспорта.

## 15. Явно отложено

- проверка неактивных WEB-прокси и авто-ротация в них;
- возобновление сессии релея между вкладками или процессами;
- relay-auth v2;
- альтернативные пути моста, порты или не-HTTPS origin релея;
- расширение `AbstractSocket` настоящим writable-backpressure для восходящего потока.
